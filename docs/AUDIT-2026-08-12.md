# Full-repository audit — 12 August 2026

A from-scratch audit of the whole repository, a re-evaluation of the
previously recorded pending items, and the fixes made in response. Five
independent read-only reviews covered security, server correctness, the
database, the web client, and the status of prior commitments; the fixes
were then made by separate writers so that no reviewer graded its own
work.

Every claim below was measured against the code or a test run. Where a
finding could not be demonstrated, that is stated rather than glossed.

## Findings and dispositions

### Critical — authority resolved without the bound organisation

`membershipOf` and fifteen other membership reads filtered on `user_id`
alone. The SELECT policy on `organisation_memberships` intentionally
carries an `OR user_id = current_user_id()` branch so the unbound
organisation picker works, and that branch remains active under a bound
tenant. Those reads therefore saw the caller's memberships in every
organisation and took an arbitrary row, with no `ORDER BY` and no
`LIMIT`.

The consequence is privilege escalation inside an organisation the caller
already belongs to: a viewer who owns any second organisation could have
the owner role and the issue/cancel authorities answer for the first.
Creating that second organisation is not itself a defect — any
authenticated user may create one, which is how organisations come to
exist — but it makes the precondition trivial. A second effect was
disclosure: the member list returned the caller's rows in unrelated
organisations.

Measured, not inferred: bound to an organisation where the user was only
a viewer, the unscoped query returned two rows with the **owner** row
first, so `const [membership] = …` yielded owner. The plan is a sequential
scan, so which row arrives first depends on heap placement and free-space
reuse — the escalation is real but not reproducible on demand.

Fixed by adding `and organisation_id = app_private.current_organisation_id()`
to every membership read that runs inside a bound-tenant transaction, in
`authz.ts`, `identity.ts`, `organisation.ts`, `export.ts` and
`amendments.ts`. The two unbound picker endpoints (`/api/me`,
`/api/organisations`) are deliberately left unscoped.

Because row order is not stable, endpoint-level tests are unreliable
discriminators here — they passed against the unfixed code in one fixture
and failed in another. The permanent guard in
`apps/server/test/cross-org-authority.integration.test.ts` instead
resolves the same user against **both** organisations in a single test: an
unscoped resolver must answer identically twice, so one assertion is
guaranteed to fail whatever the planner does. Against the unfixed code it
returned `viewer` for both bindings and failed; with the fix the file
passes 8/8.

`docs/SECURITY.md` already required "explicit query scoping plus RLS
defense in depth". The contract was right and the code did not meet it;
the rule is now stated precisely enough to be checkable.

### Low — placeholder authentication secret accepted when `NODE_ENV` is unset

`assertProductionSecret` enforced the secret only when `NODE_ENV` was
exactly `production`, so a bare start fell back to the documented
placeholder and made session cookies forgeable. The docs UI in `app.ts`
already fail-closed on an unset `NODE_ENV`; the secret gate now matches,
treating anything that is not explicitly `development` or `test` as
production.

### Receipt integrity — a challan could be issued against a closed order

`writeLines` validated the purchase-order link when a draft was saved, but
the issue route never re-read it. An order closed or cancelled in between
still accepted the receipt, and only a cancellation reopens an order, so a
closed order could silently accumulate over-receipt. The issue route now
re-checks the linked orders under the established
`purchase_orders → delivery_challans` lock order and refuses with
`PO_NOT_ISSUED`.

### Quantity ceilings were never enforced in the database

Migration 0030 enforced the amendment _floor_ — an amendment cannot reduce
a quantity below what is already delivered or installed — but nothing
enforced the _ceiling_. A direct-SQL writer, an importer or a future
handler could exceed the sanctioned quantity, and the floor would then
permanently ratify the breach.

Migration `0046` adds constraint triggers for both. Installation is capped
at the sanctioned quantity unconditionally; delivery honours
`works.allow_excess_delivery`, and a Work that cannot be read does not
lift the cap. Both take the `work_items` row lock in the order the routes
already use, because a naive sum check admits two concurrent writers —
demonstrated directly: a lock-free variant let two simultaneous 6.000
installations both succeed against a sanctioned 10.000.

The triggers were written to mirror the routes' aggregate semantics
exactly, and the unchanged server suite is the evidence that they bind the
same rule the product enforces rather than a stricter one.

### Correctness fixes

- Cancel-and-replace now takes the works row lock and `assertWorkOperable`
  that every direct cancel takes. Previously it was safe only through an
  invariant assembled from three distant places, and a completed Work
  surfaced as a bare 500 from a trigger instead of a named 409.
- The organisation export runs at `REPEATABLE READ`. Built from roughly
  forty-five sequential reads under `READ COMMITTED`, it could otherwise
  emit a referentially broken package — proven by a test that exports
  challan items whose parent Work committed mid-read.
- `purchaseOrderLineId` on a replacement line is validated when the
  correction is proposed, not only when it is approved, so a bad link no
  longer strands a request as pending with an error the approver cannot
  fix.
- Zero-quantity checks use digit inspection rather than `Number()`, so no
  float decides a refusal. This is rule-5 compliance and removes a
  dependency on a fraction-digit cap defined in another package; it is not
  reachable through the HTTP schemas today, and the discriminating test is
  therefore a unit test on the predicate.

### Web client

The one architecture-rule breach was the delivery challan total, summed
with floating point and displayed as authoritative; it now sums in exact
minor units. Timestamps that were sliced to their UTC day (showing the
previous day for Indian users before 05:30) now render the local calendar
day through a shared helper, with the date-only helper left untouched.
A bill-list refresh that could fail silently after a money-affecting
mutation now surfaces the error, and seven near-identical PDF openers
became one helper that claims the tab inside the click gesture so popup
blockers do not eat it.

Checked and found clean: no `innerHTML`/`dangerouslySetInnerHTML`
anywhere, no optimistic updates that can desync, no hardcoded hosts, and
consistent label/focus-trap handling.

### Areas verified clean

Row-level security is enabled and forced on every table with a
catalog-level assertion that fails the migration if a future table forgets
it; the application role is not superuser, owner or `BYPASSRLS`; all SQL
is parameterised; the PDF renderers escape every field; upload keys are
validated segment by segment and malware scanning fails closed; the
statutory transport reconciles unknown outcomes by lookup and never
resends; numbering is gap-free under concurrency; audit trails are
append-only. The close-versus-cancel interleaving the previous handoff
worried about was analysed and found already correct — both paths take the
same lock order — and now has the regression test it lacked.
