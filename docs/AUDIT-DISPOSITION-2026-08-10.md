# Disposition of the 10 August 2026 external audit

This document maps every finding of the external audit of
`f780b05c16ea87db6b3184ae8cb276c72da10947` (10 August 2026, 39 migrations)
to its status against the current tree (48 migrations; 0048 is a number
reserved by parallel work and not yet present). It is the item
`docs/HANDOFF-2026-08-12.md` recorded as owed.

## Provenance and scope

The source audit was supplied on 12 August 2026 as a Word document
(`auot-mb-claudev1-audit-10-08-2026.docx`). It was not in the repository
before that, which is why the handoff could not complete this mapping.

**The audit contains 44 findings, not 48.** Its numbering runs from 1 to
48, but sections 12, 24, 25 and 26 do not exist in the document. The file
carries no tracked changes, no insertions, no deletions and no comments,
so those numbers were skipped or removed before it was saved rather than
lost in extraction. The counts below are over the 44 findings that exist.
If a version containing the missing four is produced, this document must
be extended rather than assumed complete.

## Method

Each finding was verified against the current source — never against the
repository's own documentation or code comments. That distinction matters
here for two reasons. The audit itself warns that stale comments are
hazardous in compliance code because reviewers trust them as design
evidence, and the disposition work found documentation asserting fixes
that had not happened (recorded under "Documentation accuracy" below).

Verification was static: the code was read, not executed. `pnpm verify`
passed on the disposition's original tree with 46 migrations validated,
reported separately in `docs/AUDIT-2026-08-12.md`; the finding-8 and
finding-20 fixes since then each ran it again on their own branches.

## Owner dispositions

Two findings carry the owner's own decision inside the source document.
These govern; the auditor's recommendation is recorded but not applied.

**Finding 1** — the owner states that an invoice raised by the contractor
to Railways carries a SAC code and therefore does not require an e-way
bill, so e-way bills are not applicable to these invoices. The auditor's
required correction (rebuild e-way-bill generation around goods and HSN
lines) is therefore not scope. The code matches the decision: fresh
generation is refused, the NIC payload endpoint always answers 409, and
the payload builder has no call site at all.

**Finding 2** — the owner agreed with the auditor's correction, so it
remains a live requirement and is dispositioned on its merits.

## Release-blocking set

Consolidated from all four verification passes, in the order they should
be taken:

1. **Finding 8 — numbering template scope.** _Fixed in the 12 August
   follow-up._ A scope-free template (`{SEQ}` for challans, `TI/{SEQ}`
   for tax invoices) is now refused when it is saved — challan templates
   must carry `{WORK}` or `{PREFIX}`, invoice templates `{FY}` or
   `{FY2}` — and migration `0047` binds the same rule in the database,
   so the wedge can no longer be configured into existence.
2. **Finding 19 — unbounded GST rate.** _Fixed._ Migration `0048` adds
   the org-editable `gst_rates` master (rates with effective-date
   windows, retired by end-dating only); the server refuses any invoice,
   quotation-line or stated purchase-order-line rate the master does not
   notify on the document date, re-checks at submit before money is
   computed, and the `guard_gst_rate` trigger binds the same rule against
   direct SQL. A finalised document can no longer carry a rate the
   government would reject.
3. **Finding 20 — no e-invoicing applicability model.** _Fixed on this
   branch._ Migration `0049` records the owner's declaration (undeclared
   / not applicable / applicable-from, with an optional reporting window
   in days) and freezes each invoice's IRP reporting deadline at submit
   from the declaration then in force. The IRP transport — provider and
   manual paths alike — now 409s while undeclared, where declared not
   applicable, and for a fresh registration past the stamped deadline;
   reconcile-by-lookup of an unknown earlier attempt still runs, and
   local submit and cancel are never blocked. The hard gate the audit
   asked for therefore exists before any production IRP credential is
   used. The deadline machinery is deliberately shaped for finding 5's
   residue to build on: credit notes and the cancellation window should
   inherit the same frozen per-document deadline rather than invent a
   second clock.
4. **Finding 5's residue — no cancellation window, no credit-note
   state.** _Fixed on the credit-note branch._ Migration `0051` models
   NIC's 24-hour cancellation window honestly (the closing instant is
   exposed, a late provider cancel is refused before any operation
   opens, and legacy manual evidence with no provable acknowledgement
   instant is treated window-closed) and provides the lawful instrument
   after the window: the Section 34 credit note — full value against
   exactly one submitted invoice, issued gap-free per financial year,
   superseding the invoice in the same transaction and releasing its
   Measurement Book, carrying the invoice's whole IRP evidence posture
   plus finding 20's frozen reporting deadline and its own 24-hour
   window. A wrong invoice older than a day is no longer a dead end on
   the legal register.
5. **Finding 36 — owner MFA.** _Fixed in the 12 August follow-up._
   Password-only accounts holding an owner role or document authority are
   now walled out of tenant data until TOTP is enrolled, disable is
   refused for them, the two-factor lifecycle is audited, and recovery is
   an out-of-band operator procedure. The refusal flag `MFA_ENFORCE`
   defaults on in the production compose, and the security pack turned
   the operational step into a structural one: a production boot now
   refuses to start with the flag resolved off.
6. **Findings 33 and 34 — backup consistency and storage durability.**
   Together these decide whether a customer's data can actually be
   returned. A dump-then-archive over a non-atomic object store can
   restore an invoice row pointing at bytes that were never captured.
   _Half discharged 13 August:_ finding 34's atomic-write slice is done —
   object writes are temp-file + fsync + atomic rename + directory fsync,
   so a reader or a backup can no longer capture a half-written object.
   Finding 33's snapshot inconsistency (the dump and the object archive
   are still taken at different instants without quiescence) is
   untouched, and the durability half of 34 — off-host, versioned,
   encrypted storage — is infrastructure spend the owner has deferred.
7. **Finding 37, security subset** — authentication failures, tenant
   denials and backup-age alerting. _Discharged 13 August
   (production-readiness pack)._ Authentication failures, account
   lockouts, tenant-boundary denials, rate-limit rejections, upload-scan
   failures, statutory-provider outcomes and database-pool saturation are
   all collected and alertable (RUNBOOK §6); backup age was already
   exposed. Incident response now has the metrics it needs; the residual
   gaps are named in OPERATIONS.md §6 rather than implied.
8. **Finding 32, narrow piece** — run migrations before starting new
   containers, and pin the production host key instead of trusting
   `ssh-keyscan`. _Discharged 13 August (production-readiness pack)_,
   together with automatic rollback on a failed readiness gate and a
   refusal to deploy a commit with no successful CI run. The broader
   finding stays Partial: build-on-host, digest pinning and a protected
   environment are infrastructure work, not workflow work.
9. **Finding 47, money and legal subset** — cancellation with an active
   IRN, an ordinary writer being unable to invent provider status,
   raw-SQL parent immutability, and maximum money serialisation. Three
   already have guards in code and only lack the test that stops a
   regression from silently removing them. _Discharged 12 August
   (hygiene pack)_: the four subset items, plus payload byte-stability
   after a profile change, are now proved by
   `apps/server/test/finding47-provider-state.integration.test.ts`,
   `finding47-parent-immutability.integration.test.ts`,
   `finding47-money-serialisation.test.ts` and
   `finding47-snapshot-stability.integration.test.ts`.
10. **Finding 46 — external contract proof.** _Sandbox certification done
    12 August_ (`docs/WHITEBOOKS-SANDBOX-CERTIFICATION.md`). The
    production gate remains operator-owned and conditional on rotating
    the credentials exposed in the earlier provider documentation.

Findings 10 and 11 are drift-prevention rather than present defects: both
matrices are materially complete, but neither has the catalog-driven test
the audit made the acceptance condition. The export should not be
described as complete until that test exists.

## Documentation accuracy

The disposition found three places where the repository asserts something
untrue about itself. These are recorded because the audit's own warning —
that reviewers treat comments and documents as design evidence — applies
directly, and because a false claim of completion is worse than the
original gap it describes.

- `docs/UX.md:105` states that the older site-measurement surface "is
  labelled as measurement evidence rather than being presented as the
  formal Measurement Book itself." The interface still labels it
  Measurement Book (finding 30).
- `docs/OPERATIONS.md` deployment rule 6 states that "Failed health checks
  trigger rollback." When this document was written that was false: the
  workflow exited and left the new containers running (finding 32). The
  13 August production-readiness pack made it TRUE rather than softening
  the claim — the readiness gate now restores the previously running image
  ids, recreates the containers from them, and exits nonzero with both
  states logged. Rules 1 and 5 of the same section are still aspirational
  and are now labelled as such in the text itself.
- Two comments in `routes/tax-invoices.ts` — the draft buyer described
  as resolved from the newest audit event (finding 16), and a claim of
  deliberately no future-date bound above the guard that enforces one
  (finding 21) — were corrected by the same commit that introduced this
  document, which then still reported them as stale: this section
  mis-described its own commit's end state, a small instance of exactly
  the false-completion hazard it warns about. Both code comments are
  accurate; the record is corrected in the 12 August follow-up. The
  `number-series.ts` claim that a template is "proved when it is saved"
  was the third entry here; the finding-8 fix made it true.

For findings 33 and 37 the documentation was instead updated to concede
the gap honestly. That is an improvement, but it is not remediation, and
the repository's own claims should not be read as evidence that those
gates are closed. Finding 36 was in this list until the 12 August
follow-up remediated it in code; finding 37 left it on 13 August, when the
signal list `docs/OPERATIONS.md` §6 names was actually implemented and
that section was rewritten to tabulate the series that exist and name the
ones that still do not. Finding 33 remains conceded-but-unremediated.
