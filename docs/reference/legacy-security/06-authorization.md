| 8.4.1 | **Tenant isolation** | PostgreSQL RLS on every tenant table; tenant context bound per request/transaction. **The DATABASE half landed 04/08/2026 [DC-4] `2b55b12` (merged `65c2a24`); the BINDING half has not, and the status cell reflects the pair, not the half.** `migrations/0011_audit_log_rls.sql`: `ENABLE` **and** `FORCE ROW LEVEL SECURITY` on the partitioned `audit_log` parent (FORCE is what stops the table owner reading past the policy — without it isolation silently does not exist), plus policy `audit_log_tenant_isolation` whose `USING` **and** `WITH CHECK` are both `tenant_id = (select nullif(current_setting('app.tenant_id', true), ''))::uuid` — the `(select …)` wrap so the planner can hoist it to a once-per-statement InitPlan rather than re-invoke a STABLE function per row (**proof level, stated because it is weaker than it sounds:** the suite asserts the stored expression's SHAPE — `pg_get_expr(polqual)`/`pg_get_expr(polwithcheck)` each contain `select` and `current_setting` — it does not read a query plan; no `EXPLAIN`- or InitPlan-based assertion exists anywhere in this tree, grepped, so once-per-statement evaluation is designed and argued in the migration header, not measured), `missing_ok = true` so an unset GUC reads NULL instead of raising, and `nullif(…, '')` so an explicitly-blank context folds to NULL as well. Either NULL path makes the predicate NULL, which `USING` and `WITH CHECK` both treat as reject: zero rows, INSERT refused, never a default tenant. `migrations/0010_create_app_role.sql`: `automb_app` `NOLOGIN NOBYPASSRLS`, owner of nothing, granted `SELECT, INSERT` on `audit_log` and never `UPDATE`/`DELETE`/`TRUNCATE` (so the append-only trail is now an ACL, not only a comment); `0011` additionally `REVOKE EXECUTE`s both partition routines from `PUBLIC`. So the exclusion is a documented assertion, not a silent gap. **Extended 05/08/2026 to the whole tenant-scoped schema — [DC-13] `1de15eb` (`works`, `schedules`, `work_items`) and [DC-47] `4018ff2` (`contacts`), merged `a28e849`.** Each of the four lands `ENABLE` + `FORCE ROW LEVEL SECURITY` + its own `<table>_tenant_isolation` policy **in the same migration that creates the table** (`0030`/`0031`/`0032`/`0040`), with the predicate copied verbatim from `0011` — so there is no intermediate migration in which a tenant table exists unprotected, which is the window a create-now-protect-later split would open. Grants are `SELECT, INSERT, UPDATE` and never `DELETE` (soft-delete via `deleted_at` on `works`, retire-never-delete on `contacts`), and `0021` grants `automb_app` read-only access to the global `units`/`unit_aliases`. **The composite tenant FK is part of the isolation story, not schema hygiene** (a DC-13 review MAJOR): RLS cannot close cross-tenant FK smuggling, because a policy's `WITH CHECK` only validates the NEW row's own `tenant_id` while FK validation runs as an internal system check that does not apply RLS to the parent lookup — so a tenant-A row could reference a tenant-B parent by id. The fix is a `UNIQUE (tenant_id, id)` on each parent plus composite children — `schedules.FOREIGN KEY (tenant_id, work_id) REFERENCES works (tenant_id, id)` and `work_items.FOREIGN KEY (tenant_id, schedule_id) REFERENCES schedules (tenant_id, id)` — which makes the parent's tenant part of the referenced key, so the smuggling row has no valid target. Re-measured live for this audit as `automb_app` with tenant A's context: inserting a schedule whose `work_id` belongs to tenant B fails with `violates foreign key constraint "schedules_tenant_id_work_id_fkey"`, while the same insert against A's own work succeeds — the constraint discriminates, it does not blanket-deny. (`work_items.unit_id` stays a plain `REFERENCES units (id)`: `units` is the global, non-tenant table above, so there is no tenant to carry.) The 21-test coverage suite needed no allowlist edit for any of the four — that is the no-allowlist property paying out. **Three bounds, all measured for this row, none of which the cell above should be read past.** (1) **The context is self-service until DC-6.** Any session can `SET app.tenant_id` to any value; nothing kernel-side binds it per request/transaction, so today the policy separates *contexts*, not *callers*. DC-6 binds it (`SET LOCAL`, never `SET ROLE`) and DC-7 probes it through a pooled connection — a policy nobody binds a context for protects nothing, which is why this row stays `TBD`. (2) **Partition-direct access is outside the RLS layer.** Measured on a live cluster for this audit: `audit_log` reads `relrowsecurity=t, relforcerowsecurity=t` while its partition `audit_log_2031_06` reads `f, f`, and the coverage query deliberately excludes `relispartition` children. What closes it today is the ACL, not RLS — `has_table_privilege('automb_app', 'audit_log_2031_06', 'SELECT')` is **false**, and as `automb_app` a direct `SELECT … FROM audit_log_2031_06` returns `permission denied for table audit_log_2031_06` (with no context and with a wrong-tenant context alike), while the same session through the parent returns 0 rows. A future migration that GRANTs on a partition would reopen it and neither the policy nor the coverage query would notice.
