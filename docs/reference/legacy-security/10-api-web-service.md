(c) The runner (`packages/db/src/migration-runner.ts`) splices **no caller-supplied value** into statement text: per-call values (filename, checksum, advisory-lock key, `to_regclass` arguments) are bound through postgres.js tagged templates, the tracking-table identifier comes from a module constant via the `sql()` identifier helper, and the only two sites that splice text into a statement at all are both trusted-static — the `CREATE TABLE IF NOT EXISTS` tracking-table bootstrap (module-constant name) and the `DROP INDEX CONCURRENTLY IF EXISTS` crash-recovery statement, whose index name is parsed out of the migration file's own committed text and re-quoted by `quotePgIdentifier`, which doubles embedded `"`. The remaining `sql.unsafe()` calls take either a literal (`BEGIN`/`COMMIT`/`ROLLBACK`) or the migration file's own committed DDL, which cannot be parameterized at all — the whole body on the transactional path (`sql.unsafe(migration.sql)`) and, since [DC-3] `5d45235`, one call per statement on the non-transactional path. **Re-verified against that DC-3 refactor, because "executes a slice" is where a rewrite could creep in:** each slice is `sqlText.slice(start, end).trim()` of the ORIGINAL file, with the boundaries found on a length-preserving stripped copy (comments and dollar-quoted bodies overwritten space-for-space, so offsets still line up). | 16.5.1 | Uniform error contract; no stack traces/internal detail to clients | Error filter. **The first service-layer error surface landed 05/08/2026 [DC-15] `fd41517` (`packages/works/src/errors.ts`), and it comes with a measured trap for whoever builds the filter (DC-17/DC-27).** What is right already: the three typed errors carry a machine-readable `.code` plus a fixed, generic `.message` naming no constraint and no SQL — verified by probe, a duplicate work code raises `code: 'work_code_conflict'` with message `"A work with this work code already exists for this tenant."` and nothing else. `.existingWorkId` is resolved by a lookup that deliberately includes soft-deleted rows so a UI can offer undelete, and it is **tenant-scoped by effect**, re-measured here rather than taken from the review: with the same `work_code` present under tenants A and B, the conflict raised for A carried A's work id (`isA=true, isB=false`), so the field cannot become a cross-tenant existence oracle. **The trap — `.message` on the UNMAPPED path is not generic, measured on a live cluster for this audit:** any error the service does not map (probed with a foreign-key violation) is rethrown as drizzle-orm's own wrapper, whose message begins `Failed query:` and then **embeds the full INSERT statement**, table and column names and `$n` placeholders included; the outer error's `.name` is plain `Error` and its `.code` is `undefined` (the SQLSTATE lives on the wrapped cause, which is why the service's own mapping unwraps it). So an API that serializes `err.message` for anything it does not recognize ships the query structure to the client — exactly this row's finding class. The error filter must allowlist by error TYPE (`.code`/`instanceof`), never pass an unrecognized `.message` through, and this row cannot go `PARTIAL` until an integration snapshot proves an unmapped failure renders a generic body. **One route into that path was closed 05/08/2026 (`6d91c33`, [DC-15] follow-up to this audit's finding):** `createWork` branched on the `PricingShape` TS union, so any runtime string other than `'letter_percentage'` — an HTTP body's, once DC-17 lands — fell into the `per_schedule` arm, passed the service mirror, and died at the DB `CHECK` as one of these SQL-embedding unmapped errors. It now rejects an unrecognised `pricingShape` up front with a typed error naming the received value. That closes one known route, not the class: any unanticipated Postgres error still reaches the caller with the query text in `.message` | Integration snapshot | TBD |
