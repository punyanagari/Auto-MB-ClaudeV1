| 16.3.3 (same-tx atomicity is a business invariant) | Audit entry for every create/update/cancel/delete/permission change, **in the same transaction** as the mutation | Kernel audit writer. **The table this row writes to landed 04/08/2026 [DC-3] `5d45235`; the writer did NOT.** `packages/db/migrations/0003_create_audit_log.sql` creates `audit_log` — columns `id uuid DEFAULT uuidv7()`, `tenant_id uuid NOT NULL REFERENCES tenants (id)`, `occurred_at timestamptz NOT NULL DEFAULT now()`, `actor uuid NOT NULL`, `action text`, `entity_type text`, `entity_id uuid`, `details jsonb` — `PARTITION BY RANGE (occurred_at)`, monthly, with `PRIMARY KEY (tenant_id, occurred_at, id)` (tenant_id leads the PK's own backing index per ARCHITECTURE.md §4 item 1, while Postgres's rule that a partitioned table's PK must *include* the partition key is satisfied by membership, not by leading). Partition bounds are pinned to **UTC** — the routine appends a literal ` 00:00:00+00` to each bound rather than letting a bare date literal resolve against the creating session's `TimeZone` GUC (the review measured an Asia/Kolkata session and a UTC session producing bounds 5.5h apart for the same month; `packages/db/test/audit-log-partition-tz.dbtest.ts` is the regression). The partition routine ships in the **same migration** (`ensure_audit_log_partition(date)` plus the zero-arg `create_next_audit_log_partition()`), seeding the current and next month. **What this row still does not have, stated so the cell is not misread:** no writer, no same-transaction coupling, and nothing yet calls the routine on a schedule — the writer is kernel work (DC-33) and the scheduled call is DC-33/worker scope; the migration grants and revokes no privilege, so the "no UPDATE/DELETE path for the application role" discipline the migration header records is *documentation*, not an enforced control, until DC-4's RLS policies land. **That last clause is discharged as of 04/08/2026 [DC-4] `2b55b12`:** `migrations/0010_create_app_role.sql` grants `automb_app` exactly `SELECT, INSERT` on `audit_log`, and `rls-coverage.dbtest.ts` asserts `UPDATE`, `DELETE` and `TRUNCATE` all read false for that role — the append-only property is now an ACL a test reads from the live catalog, not a comment. The writer, the same-transaction coupling and the scheduled partition call remain unbuilt (DC-33), and the ACL binds only `automb_app`. The migration-running role is unaffected by both the ACL and the policy — measured on a live cluster for this audit: as that role (a superuser in the test harness) a no-context `SELECT` through `audit_log` returned rows, where the same statement as `automb_app` returned zero, `FORCE` closing the OWNER bypass but nothing closing the SUPERUSER one. So "append-only" and "non-erasable" are proven for the application role and remain operational discipline for the deploy/migration role | Integration: rollback removes both | TBD |
